# 补料幂等守卫收窄到在途状态 + 部分到货仍缺料通知

> 状态：accepted（修订 D59 幂等守卫实现口径与 D62「仍缺料沉默」口径；D59/D62 本体决策不动）

阶段 16 登记已知问题的立项修复：补料单按行部分到货 → 仓储确认入库（整单终态）→ 生产单仍缺料时，受「已入库补料单阻止再补料」守卫约束，该生产单永远无法再补（死锁），且「仍缺料沉默」让生产只能靠刷列表发现。

## 背景

- 幂等守卫 `listNonFinalByProductionOrder` 的口径是「生产来源 + status ≠ 已驳回」，把终态**已入库(3)** 也算作在途。阶段 3.6 起采购申请支持行级部分到货（`arrive_quantity`），而 `confirmReceive` 是整单终态动作——部分到货入库后生产单仍缺料，但守卫按旧口径永远拦截 `createDraft`。
- D62 的「仍缺料沉默」是在"补不了"语境下的合理选择；修复再补能力后，沉默从"无奈"变成"体验断点"。

## 决策

1. **D86：幂等守卫口径收窄到在途状态**。`createDraft` 的幂等查询只含 待采购(1)/采购中(2)/待入库确认(5)（常量 `IN_FLIGHT_STATUSES`），已入库(3)/已驳回(4) 不占用名额。防重复补料的真正闸门是既有的「当前无缺料，无需补料」实时缺口重算，不依赖宽口径守卫。同一生产单在途补料单至多一张（不变）。
2. **D87-a：补料弹窗在途提示**。生产任务单详情 VO 透出 `inFlightRequestNo`（在途补料单号）；前端补料弹窗打开时若有在途单，顶部提示「已有在途补料单 PR-xxx，待其入库后可再次补料」并禁用提交按钮（缺口行仍可查看），消除"填一屏才被拦"。
3. **D87-b：部分到货仍缺料通知**。`confirmReceive` 齐套重算仍缺 → 发「补料部分到货仍缺料」通知给生产部管理员（内容含剩余缺口摘要「物料×缺口」+ 可继续补料指引，绑 `production_order` + target_route），与「物料已齐套可领料」(D62) 互斥。
4. **齐套类通知撤旧发新**。重算时先按**标题白名单**（`revokeUnreadByBizAndTitles`，白名单 = 齐套/仍缺料两标题）撤同 biz 旧未读，再按结果发新——同 biz_type 的「关联销售单已取消」(D73) 等其他通知不受影响，重复到货也不堆积。生产单终态仍走 D21 既有 `revokeUnreadByBiz` 全撤。

## Consequence

- 部分到货终态后的剩余缺口可再次补料（D86 解锁），补料决策权留在生产（不自动建单）。
- 齐套/仍缺料通知同一时点至多一条未读，语义互斥；消息生命周期仍符合 D21/D75 范式。
- `listNonFinalByProductionOrder` 更名 `listInFlightByProductionOrder`，语义与实现一致。
- 现网无处于死锁状态的活跃生产单（修复前实测），纯行为修复，无数据迁移。
