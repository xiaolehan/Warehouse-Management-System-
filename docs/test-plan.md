## 2. 推荐执行顺序（业务流串联）

```
M1 登录与首页
  → M2 供应商 → M3 物料/成品 → M4 BOM          （主数据：一切业务的输入）
  → M5 采购流（申请→进货→入库→退货）            （库存从无到有）
  → M6 销售流（建单→出库→退货）                 （库存出口）
  → M7 生产流（任务单→补料→领料→质检→入库）      （最长链，依赖 M3/M4/M5）
  → M8 库存治理（拣货/预警/盘点）                （有库存后才有意义）
  → M9 统计分析（有业务数据后核对数字）
  → M10 协同治理（消息/公告/工作要求/审批）      （贯穿全程，集中复核）
  → M11 超管专属（用户/部门/IP/日志/参数）
  → M12 AI 助手（前置条件未满足，仅记录现象）
```

**为什么按这个顺序**：模块间有硬依赖——没有供应商和物料就建不了进货单，没有入库就没有库存可出库，没有销售单就没有退货单，没有 BOM 就建不了生产任务单。按业务流走，前一环的产出直接是后一环的输入，顺带覆盖了跨模块集成；这比孤立测模块更容易暴露「数据在模块间流动时」的问题（状态回写、库存增减、消息触发）。

**执行提示**：M5 建的测试数据（物料、库存）不要在模块间清理，留给 M6–M8 用；全部测完后统一决定数据库终态。

## 3. 模块测试

### M1 登录与首页

**为什么这么测**：登录是所有角色的入口，空库状态下首页各统计卡片/图表最容易出现除零、空指针、undefined 渲染——这是空库基线独有的测试价值，有数据后就测不到了。

**P0 冒烟**
- [ ] 每个角色逐一登录（至少 7 个 admin + superadmin + 1 个 employee），首页按角色显示不同工作台，空数据卡片显示 0 或空态，无报错弹窗
- [ ] 错误密码登录 → 明确提示「密码错误」类信息，不泄露账号是否存在
- [ ] 登录后刷新页面 → 仍保持登录态；退出登录 → 回到 /login

**P1 负测**
- [ ] 未登录直接在地址栏输入 `/business/sales` → 跳转登录页
- [ ] sales_admin 访问 `/business/annual-stats`（财务专属）→ 403 页面
- [ ] warehouse_employee 访问 `/system/employee`（人事专属）→ 403 页面
- [ ] superadmin 登录后能看到全部业务页面，但页面上的业务操作按钮应灰化/禁用（ADR-0009 只读）

**P2 边界**
- [ ] 同一账号两处登录（sa-token `is-concurrent` 配置的实际行为是什么，记录现象）
- [ ] 登录后让 token 过期（或改 localStorage token 为一个非法值）→ 接口 401，前端能引导回登录页而不是白屏

### M2 供应商管理（purchase_admin · /base/supplier）

**为什么这么测**：供应商是采购链的源头主数据，被商品和进货单引用——「删了被引用的主数据会怎样」是引用保护的典型测试点。

**P0 冒烟**
- [ ] 新建供应商（含联系人）→ 列表出现 → 编辑改名 → 详情正确
- [ ] 删除一个无引用的供应商 → 列表消失（逻辑删除）

**P1 负测**
- [ ] purchase_employee / 其他部门角色访问供应商页 → 403（该模块读也要求采购 admin）
- [ ] 供应商被商品引用后尝试删除 → 应有拦截或明确提示（记录实际行为）

### M3 物料与成品（商品资料 · /base/goods · /base/products）

**为什么这么测**：这是全系统主数据核心。**唯一性规则「物料按名称+规格唯一」（ADR-0003）** 和**字段级维护权限**（采购管进价、销售管售价、仓储全维护）是历史踩坑密集区，必须逐角色验证。

**P0 冒烟**
- [ ] warehouse_admin 建物料：填名称+规格+单位+预警库存 → 列表出现
- [ ] 建**同名不同规格**的第二个物料 → 允许，两条各自独立
- [ ] purchase_admin 编辑该物料维护进价 → 保存成功
- [ ] warehouse_admin 建成品（/base/products）→ 成品列表出现，物料列表不出现（两页二分）

**P1 负测**
- [ ] 建**同名同规格**物料 → 拒绝（唯一性冲突提示）
- [ ] purchase_employee / sales_employee 尝试新建商品 → 403（商品写要求部门 admin）
- [ ] 采购角色尝试改售价 / 销售角色尝试改进价 → 应被拒或字段不可编辑（记录实际行为）
- [ ] 已被进货单引用的商品尝试删除 → 应有引用保护（记录实际行为）

**P2 边界**
- [ ] 成品不出现在「缺货识别」和「库存预警」里（D41 口径，M5/M8 会用到，留意观察）

### M4 BOM 管理（production_admin · /base/bom）

**为什么这么测**：BOM 是生产域的根基，「成品↔物料」关系只在这里维护；建 BOM 自动落成品主档、删除 BOM 的治理规则（有未完结生产单时二次确认）都是定制逻辑。

**P0 冒烟**
- [ ] 新建 BOM：填成品名+单位+标准工期+明细行（选 M3 建的物料，填单台用量）→ 编码自动生成「{成品名}-BOM」，成品主档自动落一条（若已有同名成品则复用不重复建档）
- [ ] BOM 导出 / 模板下载 / 导入回填（xlsx 闭环）
- [ ] BOM 图片上传与查看

**P1 负测**
- [ ] BOM 明细行尝试选成品（而非物料）→ 下拉不列出成品
- [ ] 非生产/仓储角色访问 BOM 页 → 403
- [ ] 删除一个有未完结生产任务单的 BOM → 二次确认提示（M7 建单后回测）

### M5 采购流（purchase + warehouse · /business/purchase*）

**为什么这么测**：采购是**库存增加的唯一入口之一**（`increaseStock`），金额与库存双敏感。读写权限分离（`requirePurchaseReadAccess` vs `requirePurchaseModuleAccess`）曾真实导致过「仓储进入库确认页 403」的线上问题——每个角色不仅要测「能不能操作」，还要测「能不能看见页面和列表」。

**P0 冒烟（两条链路都要走）**
- [ ] **链路 A·直接进货**：purchase_admin 建进货单（选 M3 物料+供应商，填数量和单价）→ 到货 → warehouse_admin 在「物料入库确认」确认收货 → **物料库存增加、进价回写**
- [ ] **链路 B·缺货申请**：warehouse_admin 把某物料库存用到预警线以下（或建物料时预警库存设高）→ 「采购申请」页缺货识别出现该物料 → 建采购申请 → purchase_admin 认领（**逐行填预计到货时间，必填**）→ 到货提交（填价格）→ warehouse_admin 确认入库 → 库存增加
- [ ] 采购退货：purchase_admin 建退货单 → warehouse_admin 确认出库 → 完成 → 库存减少

**P1 负测**
- [ ] purchase_employee 建进货单 → 允许；但尝试「确认入库」→ 403（库存确认是 admin 权）
- [ ] sales_admin 访问采购各页面/接口 → 403（越权负测）
- [ ] 删除时间窗：**昨天**的进货单点删除 → 拦截「仅允许删除当天单据，历史单请走作废」；**当天**未入库单删除 → 成功且列表消失；历史单走**作废**（仓储审批），已入库单作废后库存正确回补
- [ ] 采购退货数量超过可退量 → 服务端拦截（不能退成负库存）
- [ ] 认领时不填行级预计到货时间 → 表单必填拦截

**P2 边界与消息**
- [ ] 采购申请行级部分到货：一行全到、一行部分到 → 确认入库后状态与库存按实到计算
- [ ] 认领后，申请人（warehouse_admin）消息中心收到**行级到货摘要**站内信，点击能跳转到对应单据（targetRoute）
- [ ] 作废一张采购申请 → 相关未读消息被撤回（D21 范式：不留「有通知无单据」的悬挂消息）

### M6 销售流（sales + warehouse · /business/sales*）

**为什么这么测**：销售是库存出口与收入源头。本系统有三个定制行为必须实测：**零库存开单**（允许超卖建单，出库时才硬校验）、**价格偏离超管审批**（阶段 5）、**履约时间线推算**（8 节点，依赖生产/采购数据）。

**P0 冒烟**
- [ ] sales_admin 维护成品售价（成品管理页单字段编辑）
- [ ] 建现货销售单（成品有库存）→ warehouse_admin 确认出库 → **成品库存减少**，单据状态/时间线推进
- [ ] 建**缺货销售单**（成品库存 0 或不足）→ 允许建单，页面有「库存不足」标识，挂在待确认队列
- [ ] 销售退货：从可退销售单建退货 → warehouse_admin 确认入库 → 库存回补

**P1 负测**
- [ ] 缺货单在库存不足时，warehouse_admin 尝试确认出库 → 服务端硬拦截（不超卖）
- [ ] sales_employee 建单允许、确认出库 403
- [ ] 改价幅度超过阈值（系统参数里的价格偏离阈值）→ 触发超管审批而非直接保存；superadmin 在「价格偏离审批」通过/驳回，两种结果的单据状态都正确
- [ ] 删除时间窗与角色：**昨天**的销售单删除 → 拦截（仅当天可删）；sales_employee 删**自己建的未出库当天单** → 允许（价格驳回后改价重提场景）；删他人单/已出库单 → 403
- [ ] 已出库销售单**作废**：库存正确回补；勾选红冲 → 生成数量/金额为负的红冲单（禁删、禁再作废）；已作废单再操作 → 拦截「禁止重复作废」

**P2 边界与消息**
- [ ] 销售单详情「履约时间线」：现货充足单只显示「下单→发货」两节点；关联生产单的单显示完整 8 节点（配合 M7 验证）
- [ ] 建单后 warehouse_admin 收到「待确认出库」站内信；删除/作废销售单 → 未读消息撤回
- [ ] 取消一张关联了生产任务单的销售单 → production_admin 收到「关联销售单已取消」通知（D73，配合 M7）
- [ ] **靶子 T4**：销售 10 件确认出库 → 部分退货 3 件确认入库 → 作废原销售单 → 观察库存：若净效果为 +13（而非 +7）则坐实双倍回补漏洞，记入问题表（代码级已确认无守卫，此为实弹验证）

### M7 生产流（production + warehouse + purchase · /business/production* · /business/qc）

**为什么这么测**：这是全系统**模块间依赖最密集**的区域——BOM、库存、采购、销售、消息五线交汇，历史开发阶段 1、11–18、24 都在修这条链。状态机最长（任务单 7 种状态），每个状态跳转都要测「该跳的能跳、不该跳的跳不了」。

**P0 冒烟（完整走一遍）**
- [ ] production_admin 建生产任务单（选 M4 有 BOM 的成品）→ 建单即出**齐套预警**（物料够=齐套；不够=部分/严重缺料）
- [ ] 缺料时 → purchase_admin 收到缺料通知站内信（含缺口明细）
- [ ] production_admin 发起**补料** → 自动生成「待采购」的采购申请（不经仓储转正，D59）→ 走 M5 链路 B 到入库 → 齐套重算 → production_admin 收到「物料已齐套可领料」或「补料部分到货仍缺料」（两者互斥不堆积，D86/D87）
- [ ] production_employee 发起**领料申请**（明细按 BOM×数量自动带出、只读）→ warehouse_admin 在拣货单「确认出库」→ 物料库存减少
- [ ] 开工 → 7 道装配工序逐道**打卡**（production_employee 可打卡，admin 可撤销）→ 质检首测记录（OK）→ 完工 → 成品测 → **生产入库** → 成品库存增加

**P1 负测**
- [ ] 未领料（或领料未全额出库）尝试开工 → 拦截（D59 开工前置）
- [ ] 质检 NG → 不返工重测直接生产入库 → 拦截；NG 后走返工→重测合格 → 可入库；不可修复 → 报废（终态）
- [ ] production_employee 尝试建/作废/终止生产任务单 → 403（admin 权）
- [ ] **靶子 T1：手动退料净额校验**——在生产单详情发起退料，尝试退「未领过的物料」或「超过已领未退净额的数量」（页面操作 + 如可能直接调 API `POST /business/production-orders/{orderId}/return`）→ 预期服务端拦截；**若放行则是已知疑似漏洞，记入问题表**
- [ ] 在途补料单存在时再次补料 → 弹窗提示在途单号并禁提交（D87-a）

**P2 边界与消息**
- [ ] 手动终止（status=7，原因必填）→ 自动生成退料单（数量=已领未退净额）→ warehouse_admin 确认回流 → 库存正确回补；履约时间线回退「待重新排产」
- [ ] 终止 vs 作废 vs 报废三者的单据展示差异（终止保留打卡/质检记录可见）
- [ ] 建任务单时关联一张缺货销售单 → 生产入库后建单销售本人收到通知；销售单的履约时间线联动推进

### M8 库存治理（warehouse · /business/pick-list · /business/stock-warning · /business/stocktake）

**为什么这么测**：库存数字的准确性是 WMS 存在的意义。盘点是阶段 23 新模块（四态状态机+盲盘+责任到行），新逻辑密度高；库存预警的「成品排除」口径容易回归。

**P0 冒烟**
- [ ] 库存预警页：把某物料库存降到预警线以下 → 出现在预警列表；成品永不出现在预警里
- [ ] 盘点全流程：warehouse_admin 建盘点单（自选商品范围，**逐行指定负责人**）→ 导出盲盘表（**默认不含账面数**）→ 页面逐行录入或 xlsx 回填 → 提交 → admin 审核生效 → 差异按「实盘 − 审核时实时库存」调整，库存正确变动

**P1 负测**
- [ ] warehouse_employee 只能录入/导入**本人负责行**，其他行输入框禁用；直接调 API 录非本人行 → 403
- [ ] 盘点单提交后、审核前，正常做一笔出入库 → 审核时差异按**生效时点**账面算（不按建单快照重复调整）

## 4. 横切测试

### 4.1 权限矩阵负测（抽测，不必全组合）

**为什么**：本系统权限是三层（路由守卫 → 按钮指令 → Service 兜底），且**读权限与写权限分离**——历史上改一处漏另一处真实发生过（`page()` 仍用旧权限导致 403）。以下组合是易错点，至少各测一次「读」和「写」：

| 角色 | 应可读（不该 403） | 应被拒（写） |
|---|---|---|
| warehouse_admin | 销售单列表、进货单列表、生产任务单列表 | 建销售单、维护售价 |
| sales_admin | 物料/成品列表 | 确认出库、建进货单 |
| purchase_admin | 物料列表 | 确认入库（仓储权）、建销售单 |
| production_employee | 生产任务单、BOM 只读 | 建/终止任务单、BOM 写 |
| 任意 employee | 首页、消息、工作要求 | 本模块外一切写操作 |
| superadmin | 全部业务页面只读（财务两模块除外——应 403） | 一切业务写（403），治理写放行 |

### 4.2 消息生命周期 checklist（每过一个业务动作勾一次）

**为什么**：D21 范式要求消息与单据同生命周期，漏接 `revokeUnreadByBiz` 就会出现「点通知进去单据已不在」的悬挂体验。

- [ ] 每个触发消息的动作（缺货通知、认领摘要、齐套/仍缺料、待出库、关联取消、终止退料）：接收方确实收到 → 内容含关键信息（单号/数量/规格）→ 点击跳转正确
- [ ] 每张单据的删除/作废/终态：相关**未读**消息消失，已读消息保留
- [ ] 同 biz 的齐套类消息不堆积（先撤旧再发新，D87）

### 4.3 已知靶子清单（调研发现，优先打）

| # | 位置 | 疑似问题 | 验证方式 |
|---|---|---|---|
| T1 | 生产退料 `createReturn` | 服务端净额校验（`ensureWithinReturnable`）只在终止路径调用，直调 API 可能退未领物料/超量退 | M7 P1：页面+API 两路尝试超量退 |
